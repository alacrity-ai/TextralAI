# Codebase Audit — 2026-05-03

> Audit conducted at the close of Phase 5 (corpus profiles + enrichment +
> reranker enablement). Five phases of feature work shipped against
> a substrate that started as a clean refactor; this is the first
> full pass to flag what's calcifying, what's drifting, and what
> would hurt to change later.
>
> The codebase is fundamentally healthy: 295 TS tests + 77 Python
> tests passing, typecheck and lint clean, two live e2e flows green
> against deployed dev. The findings below are about *future* leverage,
> not present correctness.

---

## TL;DR — top six findings

1. **Vector store binding is hardcoded.** `VECTORIZE_OPENAI_LARGE` is
   referenced literally in three files. Swapping in Qdrant (or a second
   Vectorize index for `workers_ai` 1024-dim embeddings) is a
   multi-file change. → §1
2. **Three different `resolveProviderKey` functions** with three
   different shapes. Phase 5 added a fourth call site and a workaround
   for the third's behavior. → §2
3. **D1 SQL is scattered across routes**, not behind data-access
   helpers. New write paths in Phase 5 added more inline SQL. The
   `apps/api/src/db/` layer started right but isn't being used
   consistently. → §3
4. **Schema duplication: Zod (TS) + Pydantic (Python)** maintained
   manually. The parity test catches drift, but the maintenance
   burden is real and grows with every Phase 6+ contract change. → §4
5. **`query.ts` is 891 lines.** It has ten responsibilities and is
   the single biggest review-time bottleneck. → §5
6. **R2 is in a half-state.** Native presigning isn't available;
   the Worker-proxy fallback works but every consumer call site
   has to know about both shapes. → §6

The other findings are smaller; full list below.

## §1 — Vector store: too tightly coupled to Vectorize

### Where it bleeds

```
apps/api/src/types.ts:27                       VECTORIZE_OPENAI_LARGE: Vectorize;
apps/api/src/retrieval/vectorize-query.ts:22   env.VECTORIZE_OPENAI_LARGE.query(...)
apps/api/src/routes/internal/ingest-write.ts:439  c.env.VECTORIZE_OPENAI_LARGE.upsert(...)
apps/api/src/routes/internal/ingest-write.ts:474  c.env.VECTORIZE_OPENAI_LARGE.deleteByIds(...)
```

Three direct binding-name references plus the type declaration. The
Container's `app/stages/index.py` calls `/internal/vectorize/upsert`,
which goes through `ingest-write.ts` — so the Container is
*indirectly* coupled too.

### What it costs to change

- **Adding a 1024-dim Vectorize index** (for `workers_ai` bge-large)
  requires editing all four files and routing per-binding by the
  embedding profile. The ingest stage already records
  `embedding_dimensions`; the Worker would need to switch indexes
  at upsert time.
- **Swapping to Qdrant** is a larger refactor: the binding API differs
  (`upsert` shape, `query` filter syntax, mutation semantics). Every
  call site changes.

### Proposed fix

Introduce a small `VectorStore` interface in
`apps/api/src/retrieval/vector-store.ts`:

```ts
export interface VectorStore {
  upsert(records: Vector[]): Promise<{ mutation_id: string | null }>;
  query(vector: number[], opts: { topK: number; filter: Filter }): Promise<DenseHit[]>;
  deleteByIds(ids: string[]): Promise<{ count: number }>;
}

export function vectorStoreFor(env: Env, embeddingProfile: string): VectorStore;
```

`vectorStoreFor` selects the binding by embedding profile (today only
`openai-text-embedding-3-large-1536` resolves; tomorrow extra
profiles plug in by adding a switch case + a new binding). A Qdrant
adapter implements the same interface — call sites see a single API.

**Effort:** ~half a day. Touches `vectorize-query.ts`, the two
`ingest-write.ts` handlers, and adds one interface file. Tests stay
green if we keep the existing OpenAI-1536 binding as the default.

## §2 — Provider-key resolution: three flavors of the same function

### Where they live

```
apps/api/src/auth/provider-keys.ts:21      resolveProviderKeyById(env, tenantId, id) → metadata only
apps/api/src/auth/provider-keys.ts:46      resolveProviderKey(env, tenantId, args)   → metadata + raw
apps/api/src/ingestion/dispatch.ts:188     resolveProviderKey(env, tenantId, body)   → ID only
apps/api/src/routes/query.ts:558           resolveProviderKeyForQuery(env, tenantId, ...) → ID + raw
```

Four functions, three distinct return shapes (`metadata only`,
`metadata + raw`, `id only`, `id + raw`), two different "key not
found" semantics (the dispatch one throws BAD_REQUEST when neither
ref nor ID is supplied; query one throws the same; reflang differs
slightly). Phase 5's reranker integration had to wrap
`resolveProviderKeyForQuery` in a try/catch to swallow `BAD_REQUEST`
because the rerank-config path *expects* "no key" to be a normal
state. That workaround is in `query.ts` lines 230-245.

### What it costs to change

Adding any new provider-key consumer (e.g. an admin "test this key"
endpoint) means picking from four near-clones. The "no key supplied,
fall through gracefully" semantic is foreign to all four; new code
adds new try/catch wrappers.

### Proposed fix

Consolidate into one function with a result-shape parameter:

```ts
type KeyLookup =
  | { kind: 'id'; id: string }
  | { kind: 'ref'; provider: string; ref: string }
  | { kind: 'optional_ref'; provider: string; ref?: string };  // returns null when absent

interface ResolvedKey {
  id: string;
  raw_key: string;        // populated only when caller asks for it
  meta: { /* … */ };
}

export async function resolveProviderKey(
  env: Env,
  tenant_id: string,
  lookup: KeyLookup,
  opts?: { include_raw?: boolean },
): Promise<ResolvedKey | null>;
```

Single source of D1 + Secrets Store reads, single throw-vs-null
contract, single test surface.

**Effort:** ~half a day. Updates four call sites + the rerank
workaround removal. Bonus: removes the runtime `BAD_REQUEST`
exception-as-control-flow.

## §3 — D1 SQL is scattered, not abstracted

### The signal

90 references to `c.env.DB`/`env.DB` across `apps/api/src/`. Top
files by count:

```
src/routes/internal/ingest-write.ts   11 raw SQL strings
src/routes/documents.ts                8
src/routes/provider-keys.ts            6
src/routes/query.ts                    5
src/ingestion/dispatch.ts              5
```

The `apps/api/src/db/` directory has helpers for `documents`, `jobs`,
and `namespaces` — but new code consistently bypasses them with
inline SQL. Phase 5 alone added inline UPDATE statements in three
files.

### What it costs

- Tenant-scoping is enforced by hand: every query must remember
  `WHERE tenant_id = ?`. A grep finds 34 places that do; bugs in the
  other 56 places would be cross-tenant leaks.
- Schema migrations require updating handler code in N places vs one.
- Mocking for tests is painful — every test that needs an
  ingestion_job has to know the full INSERT shape.

### Proposed fix

Two-tier:

1. **Discipline pass:** move every inline SQL string into
   `apps/api/src/db/<entity>.ts` helpers, *no exceptions*. Add a
   lint rule (or grep-based CI check) that fails if `c.env.DB.prepare`
   appears outside `src/db/`. ~one day's work.
2. **Optional follow-on:** introduce a tiny query-builder that
   structurally requires `tenant_id` (e.g.
   `tenantScopedQuery(env, tenantId).table('chunks').where(...)`).
   Phase 7 candidate; not urgent.

The first tier alone closes the "cross-tenant leak" footgun.

## §4 — Schema duplication: Zod + Pydantic

### The signal

The Phase 5 corpus profile schema lives in two places:

- `packages/corpus-profiles/src/schema.ts` — Zod, ~120 lines
- `apps/ingest/app/corpus_profiles/schema.py` — Pydantic, ~115 lines

The shapes are deliberately kept structurally identical; a parity
test catches drift. But the test is reactive — it tells you *that*
the schemas diverged, not what to do about it.

### What it costs

- Every Phase 6+ contract addition (e.g. a new `enrichment.passes[*]`
  field) requires two edits, one test update.
- Optional vs required + default handling differs subtly between the
  two libraries (the Phase 5 work hit one such case — Pydantic's
  `Optional[X] = None` vs Zod's `.optional()` serialize differently;
  fixed in the parity test by `exclude_none=True` on the Python side).
- Knowledge of "which side is canonical" is implicit. Today the
  YAML is canonical and both sides parse it; that contract isn't
  written down anywhere except this audit.

### Proposed fix

Three options ordered by ambition:

1. **Document the contract.** Add a paragraph to
   `packages/corpus-profiles/README.md` calling out the YAML as the
   canonical form, the parity test as the drift-detector, and the
   "both sides edit together" rule. Half-hour. Lowest leverage.
2. **Generate the Pydantic schema from the Zod one** (or vice versa).
   Tools exist (`zod-to-json-schema` → `datamodel-code-generator`).
   One direction stays canonical; the other regenerates on `make
   gen`. Half a day. Trades a manual sync rule for a build-step.
3. **Move to a single source of truth** — JSON Schema in YAML, both
   sides import. Eliminates Zod's nice DSL features (e.g.
   `superRefine`); a wash.

Recommendation: do (1) now, pencil in (2) for Phase 7 if the
contracts grow.

## §5 — `query.ts` is 891 lines and growing

### The signal

```
apps/api/src/routes/query.ts                  891 lines
apps/api/src/routes/internal/ingest-write.ts  480 lines
apps/api/src/routes/documents.ts              510 lines
apps/api/src/ingestion/dispatch.ts            264 lines
```

`query.ts` is by far the worst. It contains:

1. The OpenAPI route definition
2. Profile resolution wiring
3. Version-id resolution
4. Provider-key resolution wrapper
5. Embedding call
6. Hybrid retrieval orchestration
7. Reranker invocation + key resolution + fallback
8. Context assembly
9. Synthesis + structured output validation
10. Citation validation
11. Audit row finalization (~150 lines of audit-shape boilerplate)
12. R2 mirror best-effort
13. Empty/failure response helpers

Twelve responsibilities in one file. The route handler is ~330 lines
of imperative pipeline.

### What it costs

- Code review is hard: every PR touching the query path triggers a
  diff against a 900-line file.
- New features (Phase 6 streaming, Phase 7 eval-bench hooks)
  guaranteed to add complexity to the same file.
- Testing the synthesis path requires mocking everything upstream of it.

### Proposed fix

Extract a `QueryPipeline` orchestration layer:

```
apps/api/src/query/
├── pipeline.ts         ← the high-level steps (calls the modules below)
├── stage-01-resolve.ts ← profile + namespace + version
├── stage-02-embed.ts
├── stage-03-retrieve.ts ← hybrid + rerank
├── stage-04-context.ts
├── stage-05-synthesize.ts
├── stage-06-finalize.ts ← citation validation + audit + R2 mirror
└── routes.ts           ← the OpenAPI binding only
```

Each stage is ~80-150 lines, individually testable. The route
handler shrinks to ~60 lines orchestrating them.

**Effort:** one to two days. Mostly mechanical; the test surface
stays the same. Phase 6 streaming work is much easier afterward.

Phase 5 introduced its own complexity into `query.ts` (the rerank
key-resolution try/catch, profile resolution, layer-budget plumbing);
do this *before* Phase 6 not after.

## §6 — R2 is in a half-state

### The signal

`R2Bucket.createPresignedUrl` doesn't exist (Phase 3+4 Appendix C.1
documents this discovery). `presignPut` returns a sentinel URL
(`https://r2.local/...`) that callers detect and rewrite to a Worker-
proxy path. The Worker-proxy is fine but the contract is awkward:

```ts
// In apps/api/src/routes/documents.ts:
const presigned = await presignPut(c.env, key, body.content_type, body.size_bytes);
const isProxyFallback = presigned.url.startsWith('https://r2.local/');
const url = isProxyFallback ? `${origin}/v1/documents/.../data` : presigned.url;
```

Every consumer of `presignPut` must know about the fallback shape.
The Container's `worker.py` `post_bytes` is a parallel implementation
of the same idea.

### What it costs

- Two consumer code paths for "upload bytes to R2": the URL-based
  one (which never lights up) and the Worker-proxy one. Until R2
  presigning is configured, the URL path is dead code.
- The presigned-URL "expires_at" field is meaningless when the
  Worker proxy is used (the Worker uses the upload_intents row's
  TTL); but it's still in the response shape.

### Proposed fix

Two paths:

1. **Provision R2 access keys** and switch `presignPut` to actual
   SigV4. The Worker-proxy code becomes vestigial. Effort: a day to
   wire the SigV4 implementation; some operational setup. Best for
   prod where bandwidth matters.
2. **Commit to the Worker-proxy as the only path.** Delete `presignPut`
   entirely; route names go from "presigned URL" to "upload-token URL"
   and don't pretend to be S3-compatible. Effort: a few hours.

Recommendation: (2) for now, (1) when bandwidth becomes a real
constraint. Either way the half-state should be resolved.

## Smaller findings

### 7. Secrets Store is KV-backed in dev — and silently in prod too

`apps/api/src/lib/secrets-store.ts` falls through to a Workers KV
shim under the `pkey/` prefix when no Secrets Store binding is
present. Phase 3+4 Appendix C.2 calls this out, but it remains a
prod risk: the deploy-time API token doesn't have Secrets Store
permission, so prod would silently use KV too. KV is durable and
ACL'd to the Worker, but it isn't encrypted at rest the way Secrets
Store is.

**Fix:** When `ENV=prod` and the binding is absent, throw at boot.
Phase 6 ships the real Secrets Store cutover; until then, fail
loudly rather than silently downgrade.

### 8. `enrichment_status` lives on `version_indexes`, not `ingestion_jobs`

This audit caught one bug late in Phase 5: the transition handler
tried to UPDATE `ingestion_jobs SET enrichment_status` (it doesn't
exist there) which silently failed and left
`documents.current_version_id` un-promoted. The correct column is
on `version_indexes`. Fix is in place, but the design clarity is
poor: there's no obvious reason for an audit reader why the
enrichment summary lives on the index row vs the job row. Add a
comment to the migration or migrate to a clearer name.

### 9. Container can't talk to the Worker for chat (yet)

`apps/ingest/app/enrichment/runner.py` builds a chat callable that
POSTs to `/internal/providers/chat` — but that endpoint doesn't
exist on the Worker. Phase 5's enrichment passes are unit-tested
with mocked `ctx.chat` callables; live enrichment can't run until
Phase 6 ships the chat endpoint.

**Fix:** Add `/internal/providers/chat` to the Worker (mirror of
`/internal/providers/embed`). Trivial wiring; ~30 lines + tests.

### 10. `provider` namespace on identifiers is inconsistent

The codebase mixes `workers_ai` and `workers-ai` (with dash) in
different layers. `apps/api/src/providers/types.ts` has
`'workers-ai'` in one ProviderError union; everywhere else uses
`'workers_ai'`. Caught by typecheck today (the types narrow), but
fragile.

**Fix:** Lock on `workers_ai` (snake_case) everywhere. Five-minute
sweep.

### 11. `query.ts` audit-finalize is a 150-line type-by-hand object

`finalizeAudit` in `query.ts` constructs a nested object with 17
fields, twice (success path + failure path), with the type declared
inline. The `RerankerAudit` shape pulled it into a contracts file
in Phase 5; the rest of the audit shape should follow. Move it to
`packages/contracts/src/query.ts` (where `QueryAudit` already lives)
and have the route consume the contract type.

### 12. The Vectorize ID 64-byte cap isn't enforced anywhere

We hit it once during Phase 3+4 (Appendix C of that doc) and again
during Phase 5 design. There's no runtime check or unit test that
asserts a generated chunk_id stays under 64 bytes. It's load-bearing
but invisible.

**Fix:** Add an assertion in
`apps/ingest/app/enrichment/runner.py:_artifact_chunk_id` and the
generic chunker's `_chunk_id`. Both currently produce 40-44 char IDs
but a future change to ULID format or version_id width could blow it.

### 13. Stage-attempt write is unauthenticated within `internal/jobs/:id/stage-attempt`

The HMAC middleware authenticates the *caller* but the handler
trusts the body's `tenant_id` field (assertOwnership compares it
against the loaded job, which is correct) — so far so good. But the
handler accepts arbitrary `metadata` JSON without size/shape limits.
A malicious Container instance could write 1MB of "metadata" per
stage_attempt row, blowing through the D1 row size cap.

**Fix:** Cap `metadata` JSON at e.g. 16 KB; reject larger payloads
with a clear error.

### 14. Test fixture files don't exist yet

`PHASE_5_IMPLEMENTATION.md` §5.12 references
`apps/api/test/fixtures/narrative-tiny.md` and
`lease-tiny.md` for the expanded live e2e. The current `test-live-phase5.ts`
inlines the fixture content; the doc says they should live in test
fixtures. Either commit the fixtures or update the doc to match
reality.

### 15. The `_lazy_load_registry` indirection is subtle

`apps/ingest/app/enrichment/runner.py` defers submodule imports to
work around the circular import (submodules import `register_pass`
from runner). Functional, but the comment is light. Future
contributors adding a new pass module will plausibly forget to add
it to the `_lazy_load_registry` import list and silently end up with
a smaller registry.

**Fix:** Either auto-import via `pkgutil.walk_packages` (eager
discovery) or add an explicit "if you add a pass module, add it
here too" note + a test that asserts `registered_pass_ids()`
matches the YAML's pass list.

### 16. Container Dockerfile's `COPY profiles ./profiles` doesn't fail loudly when the dir is missing

If a developer forgets to run `make build-ingest` (which mirrors
the YAMLs into `apps/ingest/profiles/`), `docker build` silently
fails: there's nothing for the Dockerfile to COPY. The container
boots, then crashes at uvicorn startup when the loader can't find
profiles.

**Fix:** Add a sanity step at the top of the Dockerfile
(`RUN test -d ./profiles`) — wait, that doesn't work because the
COPY hasn't happened yet. Better: change `make build-ingest` to
`set -e && [ -d packages/corpus-profiles/profiles ] && cp -r ...`
so the COPY source is verified locally before the wrangler build.
Already partly there; tighten the error message.

### 17. ESLint config doesn't include `packages/corpus-profiles`

The flat root config covers all `**/*.ts`, but the per-package
`lint` script runs `eslint src test`, which is correct for the new
package. However, the root `pnpm -r lint` covers everything thanks
to the workspace iteration. No regression — but worth confirming
in CI configuration.

### 18. No automated check for "merge.ts in TS matches merge.py in Python"

The two `mergeProfile`/`merge_profile` implementations are intended
to behave identically. There's a unit test on each side, but no
parity test that feeds the same inputs to both and compares
outputs. Drift in merge semantics would show up at production
runtime, not at boot.

**Fix:** Extend the existing TS parity dump to also dump
`mergeProfile(generic, override)` for a representative override
matrix; have the Python parity test compare.

## Modularity / "could we swap X" matrix

| Component | Current coupling | Swap difficulty |
|---|---|---|
| Vector store (Vectorize → Qdrant / Pinecone) | High (binding name in 3 files) | **Medium-hard.** §1 fix → easy. |
| Embedding provider (OpenAI → Voyage / Cohere) | Low (Phase 2 abstraction is good here) | **Easy.** Already swappable. |
| Inference provider (OpenAI → Anthropic / etc) | Low (same Phase 2 abstraction) | **Easy.** Already swappable. |
| Reranker (Voyage → Cohere) | Low (profile YAML field) | **Trivial.** Per-namespace. |
| D1 (→ Postgres / Turso) | High (90 direct call sites; raw SQL strings) | **Hard.** Would need both an ORM-ish layer AND query-translation. §3 fix is a prerequisite. |
| R2 (→ S3) | Medium (presign abstraction half-exists) | **Medium.** §6 fix simplifies. |
| Container runtime (CF Containers → Fly / Modal / a long-running ECS task) | Medium (queue handler + DO binding are CF-specific; FastAPI app is portable) | **Medium.** Would need a new dispatch mechanism for the Worker → Container hop. |
| Workers AI binding (→ a hosted LLM) | Low (single binding, two methods) | **Easy.** |
| Cloudflare Queues (→ SQS / Kafka) | Medium (queue handler is in the Worker) | **Medium.** Producer is one call; consumer wiring lives in `index.ts`. |
| Secrets Store (today: KV; ideal: real Secrets Store) | Low (single helper file) | **Trivial.** Already designed for the swap. |

The big takeaways: D1 is the most-coupled storage layer, vector
storage is the second-most. Both have prescribed fixes above.

## Documentation gaps

These are real, not theoretical:

1. **`packages/corpus-profiles/README.md` doesn't exist.** New
   developers would need to discover the YAML-as-canonical /
   parity-test rule by reading three different test files.
2. **The `db/` helper layer's intent isn't documented.** It exists,
   but new code keeps bypassing it (§3). A short
   `apps/api/src/db/README.md` saying "all D1 SQL goes here, no
   exceptions" would change behavior.
3. **No `apps/ingest/README.md`.** The Container's role + how it
   talks to the Worker + how to test it is implicit in three
   different Phase docs.
4. **`docs/runbooks/` has only `PROVISIONING.md`.** No incident
   runbook, no DLQ-inspection runbook, no rotation runbook. Phase 6
   should land at least one (DLQ inspection) since it owns
   observability.
5. **`SECRETS.md` is honest about the KV fallback (good)** but
   doesn't yet include `VOYAGE_API_KEY` for rerank, or the new Phase
   5 secrets the bootstrap target rotates.
6. **`docs/1-DESIGN.md` §9 (Corpus Profiles)** still shows the
   illustrative `legal` YAML inline. Add a one-line pointer to
   `packages/corpus-profiles/profiles/` as the canonical bundle
   location.

## Recommended rollup before Phase 6

If we have one to two days of "tighten before adding more" budget
ahead of Phase 6 (failure surface + observability + streaming), the
high-ROI items in priority order are:

1. **§5 `query.ts` extraction** — biggest unlock for Phase 6
   streaming work.
2. **§3 first tier (move SQL into `db/`)** — closes the
   cross-tenant leak footgun before Phase 6 adds more handlers.
3. **§2 provider-key consolidation** — already paid for once in
   the Phase 5 rerank workaround.
4. **§1 vector store interface** — relatively cheap, opens the
   1024-dim embedding profile path that Phase 7 wanted.
5. **§7 secrets-store boot check + §13 stage-attempt size cap** —
   ten minutes of code, real production safety.

Items 1-4 are roughly three to four days of focused work. Items 5
are an hour each. Done in that order, Phase 6 starts on a much
flatter floor.
