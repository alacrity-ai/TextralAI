# Bugs 5-6-2026

## 1. gpt 5.x models not working

Inference with gpt-4o works just fine,
Inference with a gpt 5 model, e.g.
gpt-5.5, gpt-5.4, gpt-5.4-mini all fail.

Error message is hard for me to suss out.

api logs show:
```
provider_call {
  outcome: 'success',
  provider: 'openai',
  model: 'text-embedding-3-large',
  latency_ms: 329,
  retry_count: 0,
  via_gateway: false
}
provider_call {
  outcome: 'degraded_success',
  provider: 'voyage',
  model: 'rerank-2',
  latency_ms: 318,
  retry_count: 0,
  via_gateway: false
}
provider_call {
  outcome: 'retryable_error',
  provider: 'openai',
  model: 'gpt-5.5',
  latency_ms: 159,
  retry_count: 3,
  via_gateway: false,
  error_type: 'bad_request'
}
```

So here in the logs you can see the embedding call goes through,
The voyage call goes through.
The openai call gets a 'bad_request' error.

This indicates to me that whatever abstraction we are using to make calls to openai provider in self-hosted mode is using the wrong calling methodology.

We may need to handle both the legacy pattern, which is working (gpt-4o-mini, gpt-4o), and a different adapter for the gpt-5 series.

This bug was discovered in the self-hosted stack.

## 2. Additional Model selection quality of life

In the sandbox, right now I have to manually type in the model name I want for inference for the openai provider.  So if I want gpt4o, I need to know the exact model name is gpt-4o, or  gpt-4o-mini, or gpt-5.5, or gpt-5.4, or gpt-5.4-mini.  
Maybe keeping track of a registry of known supported models per provider, and then surfacing that as an API call would be helpful.  Then that open text field for typing in model names in the sandbox could be a select drop down.

## 3. Dimensions in pinecone/vector backends

It can be tricky to remember what dimensions the target provider vectorstore is.
Since in the sandbox we default to 1536 dimensions, I often accidently get this error surfaced to the sandbox frontend when questioning over my 1024 Pinecone namespace:
EMBEDDING_PROFILE_MISMATCH: No version_index matches the requested (chunking_profile, embedding_profile) for version ver_01KQZ5D4SD99V140CHBVME16YA

This is very unclear that it's a dimensions problem.  Do we have enough information when we create a new namespace (e.g. the lighthouse-tales) to know that it's a 1024 dimension index that we're creating that namespace in? if so, we should likely:

A) Surface a better error message when trying to query with the wrong dimension
B) Autopopulate that field to the appropriate dimension for the namespace on a new query
C) Both
